# Robot Framework

[Robot Framework](https://robotframework.org/) is a keyword-driven test
framework for embedded, web and mobile automation. The `jumpstarter-robot`
package allows us to use Jumpstarter drivers as Robot Framework keywords,
manages {term}`lease`s during the run, and adds integration with Robot
Framework's existing keyword libraries.

For more details on the specific APIs and configuration, please see the
full documentation here: {doc}`Robot Framework <../../reference/package-apis/robot/index>`

## Why Robot Framework

- **Automatic keyword generation.** Because Jumpstarter drivers already expose
  Python APIs, we can automatically generate Robot Framework keywords for all
  existing drivers.
- **IDE Integration.** A generated client resource
  describes the exporter's drivers, so [RobotCode](https://robotcode.io/)
  completes and documents them offline.
- **Lease management.** A test suite can run against a local exporter
  config, inside an existing `jmp shell`, or acquire a lease itself.
- **Existing libraries work on leased devices.**
  [SSHLibrary](https://github.com/MarketSquare/SSHLibrary),
  [AppiumLibrary](https://github.com/serhatbolsu/robotframework-appiumlibrary)
  and the
  [Process](https://robotframework.org/robotframework/latest/libraries/Process.html)
  library work automatically through Jumpstarter tunnels.

## Installation

Install `jumpstarter-robot` with the extras you need, plus your exporter's
driver packages:

```{code-block} console
:substitutions:
$ pip3 install --extra-index-url {{index_url}} "jumpstarter-robot[mobile,ssh]"
```

| Extra    | Adds                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `ssh`    | [SSHLibrary](https://github.com/MarketSquare/SSHLibrary)                                                                         |
| `mobile` | [AppiumLibrary](https://github.com/serhatbolsu/robotframework-appiumlibrary) and [adbutils](https://github.com/openatx/adbutils) |

Drivers, consoles and leases need no extra.

## Quick start

To test out the Robot Framework integration, you can run the example local test
suite located at `python/examples/robot/basic`.

To run the example test suite, use the following command:

```console
$ cd python/examples/robot/basic
$ robot -d results tests/
```

Here is what the example suite's `exporter.yaml` config looks like:

```yaml
# python/examples/robot/basic/exporter.yaml

# A mock board, served in-process by the Robot Framework examples ("local
# mode"): no controller, hardware or `jmp shell` needed.
apiVersion: jumpstarter.dev/v1alpha1
kind: ExporterConfig
metadata:
  namespace: default
  name: mock-bench
endpoint: ""
token: ""
export:
  dut:
    type: jumpstarter_example_robot.mockdut.MockDut
    children:
      power:
        type: jumpstarter_example_robot.mockdut.MockDutPower
        config:
          board: dut
      console:
        type: jumpstarter_example_robot.mockdut.MockDutConsole
        config:
          board: dut
  storage:
    type: jumpstarter_driver_opendal.driver.MockStorageMuxFlasher
  shell:
    type: jumpstarter_driver_shell.driver.Shell
    config:
      methods:
        hello: "echo \"$GREETING $@\""
        fail: "echo \"failing on purpose\" >&2; exit 3"
```

Each Robot suite imports the `client.resource`, generated from `exporter.yaml`:

```robotframework
*** Settings ***
Documentation    Generated by `jmp robot generate` from exporter config exporter.yaml (device MockBench, session default). Do not edit: regenerating overwrites it.
Library    jumpstarter_robot.Jumpstarter    auto_import=False
Library    jumpstarter_robot.Session    default    exporter_config=${JMP_EXPORTER_CONFIG}    selector=${JMP_SELECTOR}    lease_name=${JMP_LEASE_NAME}    config=${JMP_CLIENT_CONFIG}    AS    session.default
Library    jumpstarter_robot.Driver    dut    client=jumpstarter_example_robot.client.MockDutClient    prefix=Dut    session=default    AS    dut
Library    jumpstarter_robot.Driver    dut.power    client=jumpstarter_driver_power.client.PowerClient    prefix=Dut Power    session=default    AS    dut.power
Library    jumpstarter_robot.Driver    dut.console    client=jumpstarter_driver_network.client.NetworkClient    prefix=Dut Console    session=default    AS    dut.console
Library    jumpstarter_robot.Driver    storage    client=jumpstarter_driver_opendal.client.StorageMuxFlasherClient    prefix=Storage    session=default    AS    storage
Library    jumpstarter_robot.Driver    shell    client=jumpstarter_driver_shell.client.ShellClient    prefix=Shell    session=default    methods=hello,fail    AS    shell

*** Variables ***
${JMP_EXPORTER_CONFIG}    ${CURDIR}/exporter.yaml
${JMP_SELECTOR}    ${EMPTY}
${JMP_LEASE_NAME}    ${EMPTY}
${JMP_CLIENT_CONFIG}    ${EMPTY}
```

The resource file provides access to all of the Jumpstarter drivers and
Robot Framework keywords for those drivers. Keywords are automatically generated
from the Python API signatures and custom keywords can be defined per-driver.

Here is what a test suite looks like:

```robotframework
*** Settings ***
Documentation       Power the mock board and talk to it over its serial console.
...
...                 ``Dut Power ...`` keywords come from the board's power driver, at
...                 ``dut.power``, through the generated ``client.resource``.
...                 ``Open Console`` and the ``Console ...`` keywords work on any driver
...                 byte stream.

Resource            ../client.resource
Test Teardown       Close All Consoles


*** Test Cases ***
Board Boots To Login Prompt
    Dut Power Off
    Open Console    dut.console    prompt=root@mockdut:~#${SPACE}
    Dut Power On
    ${boot}=    Console Login    root    not-a-secret    timeout=30s
    Should Contain    ${boot}    Starting kernel
    ${kernel}=    Console Execute Command    uname -r
    Should Be Equal    ${kernel}    6.6.0-mock
```

The first keyword that needs the exporter starts it, and the run stops it at
the end, so no suite setup is needed. `Dut Power Off` and `Dut Power On` come
from the board's power driver; `Open Console` and the `Console ...` keywords
work on any driver byte stream. `results/log.html` records every keyword, its
arguments and the console output.

To run the test suite from within the `jmp shell`, we can do the following:

```console
$ jmp shell --exporter-config exporter.yaml -- robot -d results tests/
```

We can also run this suite against remote exporters with the same drivers:

```console
$ jmp create lease -l board=mock --duration 1h
$ robot -d results -v JMP_SELECTOR:board=mock tests/power_and_console.robot
```

Here, `jmp create lease` leases an exporter labeled `board=mock` from the
{term}`controller`, and the run attaches to that lease because its
`JMP_SELECTOR` is the same. `JMP_LEASE=<name> robot -d results tests/` names
the lease instead (see [Lease management](#lease-management)). The run leaves
the lease active; delete it with `jmp delete lease <name>` when you are done.

## Client resources

`jumpstarter-robot` can automatically generate a
[resource file](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#resource-files)
that imports the Jumpstarter libraries, configures the exporter lease,
and imports driver keyword libraries. Test suites import the resource to use the
drivers' keywords and provide IDE completions.

### Generating a client resource

1. Add the following to the end to your project's  `robot.toml`:

```toml
[tool.jumpstarter.client.default]
exporter-config = "exporter.yaml" # The path to your exporter config
resource = "client.resource" # The resource file path to generate
```

2. Run the following command to generate the resource file:

```console
$ jmp robot generate
default: wrote client.resource (5 driver libraries)
```

`jmp robot` is available once `jumpstarter-robot` is installed alongside the
Jumpstarter CLI; `jmp-robot` is the same command from `jumpstarter-robot`
alone.

Once the resource file is generated, it can be shared with other developers
to make running Robot test suites easy.

If you do not have the exporter config, you can capture the drivers from a
lease using:

```console
$ jmp shell --selector board=rpi4 -- jmp robot generate --capture
```

### Keyword names

A driver's keywords are its path followed by the method name. For example,
the `cycle` method of `dut.power` is `Dut Power Cycle`, and the `flash` method
of `storage` is `Storage Flash`.

Aliases can be added in your `robot.toml` for convenience.
With `roles = true`, as in `python/examples/robot/multi-dut`, identical boards
share one `Power On` and `Use Device` selects the DUT to run the command on.

`Call Driver` calls any client method by path, including methods without a
keyword, and converts text arguments to the method's annotated types.
`List Driver Keywords` and `List Drivers` show what an exporter offers:

```robotframework
Call Driver    dut.power    cycle    wait=5
${keywords}=    List Driver Keywords    dut.power
```

## Writing and running tests

With a client resource in place, write and run tests from your editor or
try keywords interactively.

### IntelliSense in VS Code with RobotCode

[RobotCode](https://robotcode.io/) reads the keywords of every imported
library. A client resource names each driver's client class, so RobotCode
lists every driver keyword with its arguments and documentation, with no lease
or network:

1. Install the
   [RobotCode extension](https://marketplace.visualstudio.com/items?itemName=d-biehl.robotcode).
2. Run **RobotCode: Select Python Environment** and choose the environment with
   `jumpstarter-robot` and your driver packages installed.
3. Import the generated resource: `Resource    client.resource`.
4. Put the Robot Framework settings in a `robot.toml` next to the tests;
   RobotCode uses them to run, debug and resolve imports:

   ```toml
   paths = ["tests"]
   output-dir = "results"
   python-path = ["."]
   ```

5. After regenerating a resource, run **RobotCode: Clear Cache and Restart
   Language Servers**.

The run and debug buttons and the Test Explorer then work on any suite file
or folder. Plain `robot` ignores `robot.toml`; pass the same options on the
command line (`-d results`, `--pythonpath .`).

To run tests from the editor against a leased board, create a lease using the
same selector specified in your `robot.toml`, variables, or testbed:

```console
$ jmp create lease -l board=rpi4 --duration 4h
```

Now, if you run a test or suite from the IDE, it attaches to the existing
lease automatically and leaves it active for the next run (see
[Lease management](#lease-management)). Delete the lease with
`jmp delete lease <name>` when you are done.

### Interactive sessions with the RobotCode REPL

RobotCode's [REPL](https://robotcode.io/guides/cli/repl/) runs keywords one
at a time, which is handy for exploring a board or trying a keyword before
putting it in a test. Jumpstarter keywords work there as they do in a run.
Start it from the example folder:

```console
$ cd python/examples/robot/basic
$ robotcode repl
```

With a local exporter, the session opens at the first keyword that needs it:

```robotframework
Import Resource    ${CURDIR}/client.resource
Dut Power On
Open Console    dut.console    prompt=root@mockdut:~#${SPACE}
${kernel}=    Console Execute Command    uname -r
```

For remote exporters, acquire a lease with `Acquire Lease` and let Jumpstarter
discover its drivers. It imports a keyword library for every driver on the exporter,
`List Drivers` shows the tree and `List Driver Keywords` gives the keyword
names to type:

```robotframework
Import Library    jumpstarter_robot.Jumpstarter
${lease}=    Acquire Lease    selector=board=rpi4
List Drivers
List Driver Keywords    dut.power
Dut Power On
Release Lease
```

A second session's keywords carry its name when they would clash with the
first's: after `Acquire Lease    selector=role=sim    session=sim`, its power
driver answers to `Sim Dut Power On`. Keywords imported this way exist only while
the REPL runs; a generated client resource puts them in the editor's
IntelliSense. Sessions close when the REPL exits, releasing the leases they
acquired. `Acquire Lease` first attaches to a matching lease created with
`jmp create lease` (see [Acquire Lease and Release Lease](#acquire-lease-and-release-lease)),
and that lease stays active for the next REPL.

## Lease management

A run gets its {term}`lease` from the {term}`controller` in one of three ways:

1. **Attach to a lease created outside the run.** Create it with
   `jmp create lease`, then name it with the `JMP_LEASE` environment variable,
   or let the run find it: a session with a selector attaches to this client's
   active lease with exactly the same selector. This is how runs from the IDE
   work with no extra settings.

   ```console
   $ jmp create lease -l board=rpi4 --duration 4h
   $ robot -d results -v JMP_SELECTOR:board=rpi4 tests/   # attaches to the matching lease
   $ JMP_LEASE=<name> robot -d results tests/              # attaches to the named lease
   ```

2. **Run inside `jmp shell`.** Every session uses the shell's lease:

   ```console
   $ jmp shell --selector board=rpi4 -- robot -d results tests/
   ```

3. **Acquire it programmatically** with `Acquire Lease`, for example in the
   suite setup of the suite folder's `__init__.robot`. It acquires a lease for
   the session's selector, unless a matching lease already exists, and the
   run releases the lease it acquired when it ends. The lab example's
   `tests/__init__.robot` does this:

   ```robotframework
   *** Settings ***
   Resource       ../client.resource
   Suite Setup    Acquire Lease    session=board
   ```

The run never releases a lease it attached to. Only `Acquire Lease` acquires
one: a session that opens on its own, at the first keyword that needs it, and
finds no lease to attach to fails with a message that names these three ways.

{term}`Local mode <local mode>` is not a lease: a session that declares only
an exporter config, like the [Quick start](#quick-start) suite's, serves it
in-process.

`JMP_SELECTOR` and `JMP_LEASE_NAME` (the name of a lease to attach to) are the
`default` session's variables. A client with its own session name, such as
`[tool.jumpstarter.client.rpi4]`, gets that name in its variables
(`JMP_RPI4_SELECTOR`), so two client resources in one suite keep their own
values. `JMP_SELECTOR`, `JMP_LEASE_NAME` and `JMP_CLIENT_CONFIG` still apply
to a named session that has no value of its own.

### Acquire Lease and Release Lease

- `Acquire Lease` connects a session (`session=`, `default` if omitted) and
  returns the lease name. Arguments you leave out come from the session's
  declaration, such as the client resource or the testbed, so
  `Acquire Lease    duration=2 hours` keeps the resource's selector. Inside
  `jmp shell` it uses the shell's lease.
- `Release Lease` disconnects the session. It releases the lease only if
  `Acquire Lease` acquired it, and does nothing when the session is not
  connected.

Before acquiring a new lease, `Acquire Lease` attaches to an active lease of
the same client with exactly the same selector, if there is one: the same
labels in any order, never a narrower or wider one, and never a lease another
session of the run holds. A lease it attached to, either this way or with
`lease_name=`, is never released, so a lease created with `jmp create lease`
survives the run. `reuse=False`, or `reuse-lease: false` in a testbed, turns
this off. With reuse off, a session opening on its own does not look for a
matching lease either: only a named lease or `Acquire Lease` connects it.

```robotframework
Acquire Lease    selector=board=rpi4                  # attaches to a matching lease, or acquires one
Acquire Lease    selector=board=rpi4    reuse=False   # always a new lease
Acquire Lease    lease_name=my-lease                  # attach; never released
Release Lease                                         # releases only a lease acquired here
```

On a session that declares only an exporter config, `Acquire Lease` serves it
locally and returns no lease name, so one suite setup works on the bench and
in the lab. On a session that is already connected it returns that
session's lease; given a new selector, exporter name or lease name, it fails.

{doc}`Sessions and leases <../../reference/package-apis/robot/sessions-and-leases>`
covers several sessions, identical devices, lease ends and CI.

### Testbeds

We recommend describing each place your tests run, such as a local mock, a
lab or a CI pool, as a *testbed*: a
[YAML variable file](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#variable-file-as-yaml)
that says where every session connects, next to the test data that goes with
it. The suites and client resources stay the same; only the testbed changes.
The example in `python/examples/robot/lab` runs the same suites with three
testbeds:

| Testbed | Runs on |
| --- | --- |
| `testbeds/mock.yaml` | The mock board, served in-process ({term}`local mode`) |
| `testbeds/lab.yaml` | A lab board matching its selector |
| `testbeds/lab-pool.yaml` | A board per process from a pool, for pabot (`reuse-lease: false`) |

```yaml
# python/examples/robot/lab/testbeds/lab.yaml
JUMPSTARTER:
  config: lab                  # client config alias (`jmp config client list`), a YAML path, or env
  selector: board=mockdut,lab=eu
  duration: 1 hour
PASSWORD: change-me            # better: robot -v PASSWORD:... or a Python variable file reading a secret
```

The suite folder's `tests/__init__.robot` connects the board once for every
suite, with `Suite Setup    Acquire Lease    session=board`. With `lab.yaml`
it attaches to a matching lease of your client, or acquires one and releases
it at the end of the run; with `mock.yaml` the session has only its exporter
config, so it serves the mock board:

```console
$ cd python/examples/robot/lab
$ robot -d results -V testbeds/lab.yaml tests/
```

Keys under `JUMPSTARTER` apply to every session; a suite that imports several
client resources can set per-session values under `sessions`. A testbed
overrides the resources' defaults, and a session variable given with `-v`
(such as `-v JMP_BOARD_SELECTOR:board=x`) overrides the testbed. In RobotCode,
list the testbeds as profiles in `robot.toml`, then switch between them in the
editor:

```toml
[profiles.lab]
description = "A board from the lab controller: your lease for the selector, else a new one"
variable-files = ["testbeds/lab.yaml"]
```

Adding a lab, a board type or a CI pool then means adding a testbed, not
editing suites. See
{doc}`Sessions and leases <../../reference/package-apis/robot/sessions-and-leases>`
for every key.

### Running in parallel

[pabot](https://github.com/mkorpela/pabot) runs suites in parallel processes,
each its own Robot Framework run with its own sessions. With
`testbeds/lab-pool.yaml`, each process's suite setup acquires its own board
from the pool the selector matches and releases it at the end. The testbed
sets `reuse-lease: false`, so that processes never attach to the same lease
created outside the run:

```console
$ pabot --processes 4 -d results -V testbeds/lab-pool.yaml tests/
```

With `testbeds/mock.yaml`, each process serves its own mock board.

## Working with drivers

Keywords that work across drivers: consoles, mobile apps through Appium, and
remote libraries running on the device.

### Consoles

The console keywords read and write any driver byte stream (a serial port, a
network connection, a QEMU console) like a terminal, following the
conventions of the
[Telnet](https://robotframework.org/robotframework/latest/libraries/Telnet.html)
library:

```robotframework
Open Console    dut.console    alias=serial    prompt=root@dut:~#    timeout=2 min
${boot}=    Console Read Until    Starting kernel
Console Login    root    ${PASSWORD}
${output}=    Console Execute Command    dmesg | tail
Console Should Not Contain    Kernel panic    duration=10s
```

Output is buffered from the moment the console opens, and everything received
is written to `results/jumpstarter/console-<alias>-<n>.log`. For more console
options, driver contexts, streams and SSH, ADB and iOS connections, see
{doc}`Devices and apps <../../reference/package-apis/robot/devices-and-apps>`.

### Mobile app testing with Appium

Jumpstarter targets with an `appium` child (see
[Appium UI Automation](ui-automation.md)) work with
[AppiumLibrary](https://github.com/serhatbolsu/robotframework-appiumlibrary).
`Start Appium` serves the target's Appium on a loopback HTTPS port and returns
its `url` and the `capabilities` the target fixes. AppiumLibrary's
`Open Application` opens the session, and all of
[its keywords](https://serhatbolsu.github.io/robotframework-appiumlibrary/AppiumLibrary.html)
then act on the app:

```robotframework
*** Settings ***
Library     AppiumLibrary
Resource    ../client-android.resource

*** Test Cases ***
Settings Opens
    Device Power On
    ${appium}=    Start Appium    emulator.appium
    Open Application    ${appium.url}    &{appium.capabilities}
    ...    appium:appPackage=com.android.settings    appium:appActivity=.Settings
    Wait Until Page Contains Element    class=android.widget.FrameLayout    timeout=20s
    Capture Page Screenshot
    [Teardown]    Run Keywords    Close All Applications    AND    Stop Appium
```

`python/examples/robot/mobile` runs one set of tests on an Android emulator
and an iOS simulator; see
{doc}`Devices and apps <../../reference/package-apis/robot/devices-and-apps>`.

## Adding keywords to drivers

Every public method of a `DriverClient` subclass is a keyword, including
clients from your own driver packages outside the Jumpstarter repository.
Type hints and docstrings on client methods become the keyword's argument
conversion and documentation. To curate keywords, use the decorators in
`jumpstarter.client.decorators.robot`. They mirror Robot Framework's
[`@keyword` and `@not_keyword`](https://robotframework.org/robotframework/latest/RobotFrameworkUserGuide.html#keyword-decorator)
from
[`robot.api.deco`](https://robot-framework.readthedocs.io/en/stable/autodoc/robot.api.html)
without making the driver depend on Robot Framework:

```python
from jumpstarter_driver_composite.client import CompositeClient

from jumpstarter.client.decorators import robot


class MockDutClient(CompositeClient):
    @robot.keyword("Reboot", tags=["power"])
    def reboot(self, wait: float = 1.0) -> None:
        """Power cycle the board, waiting ``wait`` seconds while it is off."""
        self.power.cycle(wait)

    @robot.not_keyword
    def raw_status(self) -> str | None:
        """Python-only helper; hidden from Robot Framework."""
        return self.power.status()
```

The driver's prefix is still added, so on the `dut` driver this keyword is
`Dut Reboot    wait=5`, or `Board Reboot` with the alias `Board`.
`@robot.library(auto_keywords=False)` on the class exposes only
`@robot.keyword` methods.

## Examples

The examples are in `python/examples/robot`, one folder each with its own
README, `robot.toml` and tests:

- `basic`: the mock board from the [Quick start](#quick-start): power,
  console, storage, shell methods and curated keywords
- `multi-dut`: two identical boards, with role libraries and `Use Device`
- `lab`: testbeds for the `basic` board, lab boards and a pool, and parallel
  runs with pabot

  port forward
- `linux-ssh`: a Linux machine with SSHLibrary through a Jumpstarter SSH
  driver
- `mobile`: Android emulator and iOS simulator apps with Appium
